## Arti status dan confidence

- **Confirmed**: dapat dibuktikan langsung dari source, konfigurasi, dokumentasi, test merah, atau workflow.
- **High confidence**: ditemukan berulang dan alur source mendukung, tetapi belum direproduksi pada runtime.
- **Needs runtime verification**: risiko masuk akal, tetapi behavior framework atau lifecycle perangkat harus diuji.
- **Product decision required**: implementasi bergantung pada aturan bisnis yang belum dikunci.
- **Product gap**: fitur memang belum tersedia dan bukan regression.

Confidence berdasarkan jumlah audit:

- `4/4`: sangat kuat;
- `3/4`: kuat;
- `2/4`: menengah-kuat;
- `1/4`: perlu validasi tambahan, kecuali bukti source atau CI sudah eksplisit.

## Temuan detail

### CON-001 — Update stok pembelian memakai snapshot lama

Prioritas: **P0**  
Area: `OperationsRepository.recordPurchase()`  
Confidence: **2/4, tinggi**

`PurchaseDraft.lines` dapat memuat beberapa baris yang menunjuk produk atau varian sama. Seluruh baris di-resolve lebih dulu dan menyimpan snapshot entity, lalu stok diperbarui satu per satu dari snapshot tersebut.

Contoh:

- stok awal `10`;
- baris pertama `+3`;
- baris kedua `+5`;
- purchase item dan stock movement mencatat total `+8`;
- update kedua dapat menimpa update pertama sehingga stok akhir menjadi `15`, bukan `18`.

Dampak:

- saldo stok aktif berbeda dari histori movement;
- laporan persediaan tidak dapat dipercaya;
- bug berlaku untuk produk biasa dan varian.

Perbaikan wajib:

1. kelompokkan baris berdasarkan `(productId, variantId)`;
2. jumlahkan `baseQuantity` memakai operasi overflow-safe;
3. ambil dan update stok satu kali per target;
4. pertahankan purchase item serta movement per baris;
5. pastikan seluruh operasi tetap dalam transaksi Room.

Regression test:

- dua baris produk sama;
- dua baris varian sama;
- varian berbeda tetap terpisah;
- overflow membatalkan purchase, cash, debt, movement, dan update stok;
- saldo akhir sama dengan stok awal ditambah total movement.

### CON-002 — Lifecycle external file picker dan sesi Owner

Prioritas: **P0**  
Confidence: **4/4, sangat tinggi**

`externalOwnerFlowDepth` mencegah auto-lock saat Android membuka file picker. Tujuannya benar, tetapi dua masalah harus dibedakan.

#### Bug terkonfirmasi

`ReportSession.lock()` mengubah state unlocked tanpa mereset `externalOwnerFlowDepth`. Urutan berikut dapat meninggalkan guard lama:

1. unlock;
2. begin external flow;
3. lock manual;
4. unlock lagi;
5. auto-lock berikutnya dilewati karena depth lama masih aktif.

Perbaikan minimum:

- reset `externalOwnerFlowDepth = 0` di `lock()`;
- sinkronkan seluruh mutasi state;
- tambah regression test stale guard.

#### Risiko lifecycle yang tetap harus diuji

Reset pada `lock()` belum membuktikan seluruh lifecycle file picker aman. Skenario wajib:

- pilih file normal;
- cancel;
- Home atau recent task saat picker terbuka;
- rotasi atau activity recreation;
- callback gagal atau tidak kembali;
- process mati;
- Owner keluar sebelum callback;
- URI invalid atau permission ditolak.

Target behavior:

- flow picker normal tidak mengunci Owner terlalu dini;
- app yang benar-benar ditinggalkan tidak menyisakan area Owner terbuka;
- process recreation selalu membutuhkan autentikasi ulang;
- callback ganda atau terlambat tidak menghidupkan guard basi.

### CON-005 — Checkout tidak memvalidasi varian milik produk

Prioritas: **P1**  
Confidence: **tinggi dari bukti source**

    "Varian tidak sesuai produk"

### CON-013 — Metode DP piutang tidak konsisten

Prioritas: **P1**  
Confidence: **source-confirmed, satu audit**

Pada transaksi kredit dengan DP:

`CREDIT` menjelaskan jenis transaksi, bukan media uang yang diterima.

Keputusan MVP yang disarankan, tetapi belum dikunci:

- DP hanya tunai sampai UI menyediakan pemilih metode DP;
- debt payment dan cash entry memakai `CASH`;
- sale tetap `CREDIT`.

## Scope PR konsolidasi audit

PR yang memperkenalkan dokumen ini hanya:

- mengganti audit lama dengan hasil konsolidasi empat audit;
- menghapus dua workflow bootstrap sementara;
- tidak mengubah source Kotlin, schema Room, behavior aplikasi, atau metadata APK;
- tidak mengklaim test/build/runtime lulus.

Perbaikan kode dibuat dalam PR terpisah agar perubahan P0/P1 dapat direview, dites, dan di-rollback secara jelas.
